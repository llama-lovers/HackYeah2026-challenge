## Settings and Feedback Contract

| Setting | Initial/effective value | Persistence and failure behavior |
|---------|-------------------------|----------------------------------|
| Output mode | screen_reader, established in Wave 1 | Reuse outputMode; explicit browser_tts selection requires an available normalized pl-PL voice. Cancel old-route work when changing mode. Failed selection/write preserves the prior effective mode. |
| Earcons | Enabled is the existing reversible 04-02/04-03 planning assumption, not an approved user default | Reuse one validated Boolean preference; make the effective checked state explicit. User approved the off switch and cue behavior, not this initial value. It may be revised without redefining cue semantics. |
| Verbosity | Existing standard default, or exact valid stored value | Reuse verbosity and concise/standard/detailed decoder. Voice commands and options edit the same preference. |
| Privacy preview | Closed/off by default, required by SAFE-07 | Explicit inspection only. Keep payload/command/effect data ephemeral; do not persist preview contents or restore them after reopening. |

Initialize native controls from decoded stored preferences before allowing a save; show a concise loading status while initialization is pending. On storage-read failure expose fixed Polish feedback and safe decoded defaults, without claiming a successful save. During a write show Zapisywanie ustawienia… and prevent duplicate changes to that control; retain its position and restore keyboard availability after completion. On failure roll back to the last confirmed effective native state and announce the approved save-failure copy. A successful write gets one polite status message. Listen to relevant local storage changes so spoken verbosity changes and other options windows are reflected without moving focus.

Use pre-rendered role=status, aria-live=polite regions for ordinary availability/save feedback. Reserve the existing focused role=alert for trusted recovery. Associate helper/error descriptions with their controls via aria-describedby where appropriate. Never automatically narrate options statuses through chrome.tts as well as native screen-reader semantics.

Show actual voice name and local/remote metadata as text. When no Polish voice is available, keep the output controls accessible, preserve the prior route and provide the fixed recovery next step. Do not infer whether a screen reader is running from voice inventory or delivery failure. Browser voice may be remote; do not describe it as necessarily offline.

## Audio and STOP Contract

User-locked behavior: five distinct short nonverbal cues, an accessible off switch, no overlap with agent-owned browser TTS, and immediate explicit STOP handling. Cue frequencies/contours and the default-on preference are implementation/planning choices, not locked user answers.

| Cue | Trigger | Ownership and content rule |
|-----|---------|----------------------------|
| Microphone opens | Recorder has actually started | One cue per capture, not at permission-request dispatch. |
| Microphone closes | Capture microphone tracks have actually been released | Once-only normal/cancellation boundary; never resurrect a canceled processing/done cue. |
| Working | First owned recording-to-processing transition | Short finite cue, no looping audio. |
| Done | Successful owned terminal outcome | Do not play for cancellation, refusal, error or failed storage. |
| Needs confirmation | Pending interaction is successfully stored | Cue accompanies a spoken confirmation question; the question remains words. |

Use five finite, distinguishable contour/rhythm patterns. The plan's roughly 80–300ms range is an initial tuning target; actual distinction and acceptable loudness require listening evidence. Bound all gains, oscillators and queues. Cues run in the offscreen document. Microphone analysis must never connect to speakers.

Serialize agent-owned cues with browser TTS: do not start a cue while TTS is playing; let an appropriate short cue finish before starting its related spoken line, or drop a stale cue rather than delay urgent speech/control work. A confirmation cue precedes its question. STOP cancels playing/queued tones immediately; no canceled tone may start after owner invalidation. For screen-reader mode schedule related cues before agent live-region output where possible; this does not assert control over speech independently queued by NVDA or another screen reader. Tests must establish browser-TTS/cue exclusivity, not infer it from request dispatch timestamps.

With earcons enabled, routine cues replace redundant routine words. With earcons disabled, concise lifecycle text uses the selected route. Confirmation questions, refusals, action/effect messages and error next steps remain words in either setting. A cue failure cannot strand a turn or remove required confirmation/error text; provide selected-route lifecycle feedback where a cue cannot be delivered. Ordinary microphone-permission grant does not launch command recording.

Silence completion uses speech onset, then a configurable/testable trailing-silence window initially set near 1.2 seconds. This duration is a tuning default, not a hard acceptance threshold. Initial quiet and short hesitation do not clip speech; keep the existing 25-second cap. Silence/toggle/cap finalize normally once, in WebM and WAV. Safety STOP discards capture and cannot upload it. Do not add a silence-duration control to the options page solely because the internal policy is tunable; the requirement is a named configurable/testable policy.

The dedicated keyboard stop is immediate at handler entry; already-recognized complete stop/zatrzymaj commands invoke the same urgent cancellation before pending/model routing. Batch spoken STOP is known only after recording ends and transcription returns. Keep the established latency copy visible. Do not imply a closed microphone detects speech continuously. Cancellation prevents future owned output/actions and drops pending work; it cannot undo a committed DOM effect or guarantee interruption of speech already queued inside external assistive technology.

## Privacy Preview Contract

Follow the full-envelope scope selected in 04-03 and required by its exactness acceptance. Show the locally reconstructed complete model JSON body, including model, fenced messages, strict response schema, provider requirements, temperature, max_tokens and stream. Use the shared pure request representation and parity-tested Python/TypeScript provider-envelope contract. An unavailable/stale contract must yield unavailable feedback rather than an incomplete payload labeled exact. API authentication is server-held transport data; no key enters the preview.

Preview types have Polish labels: Opis strony, Dostępne działania, Polecenie, Wynik ostatniej akcji. A command preview requires the labeled field Polecenie do podglądu and explicit locally entered command text. Summary/actions use fresh masked evidence from the established target tab/document. Effect preview exists only for last actual in-memory effect inputs belonging to that still-live document. Do not invent a next command, action result or effect diff.

Target an established eligible tab/document from successful page access; opening options must not retarget to the options tab. Reject while recording/processing, a confirmation or effect is pending, or the target is missing/stale/unavailable. Recheck document identity and existing access. An empty snapshot/candidate set is an explicit unavailable state rather than fabricated content. Preserve existing masking and ordinary parcel-number positive controls.

Display a short target/freshness line and one labeled readonly plain-text textarea for the complete bounded JSON. Do not put the payload in a live region; readiness is announced separately. Never use innerHTML or execute page markup. Wrap long lines visually without changing the underlying value. The payload may scroll vertically in a keyboard-operable readonly control, with a normal-page escape by Tab/Shift-Tab and no focus trap. Do not silently truncate the provider envelope. If a complete body exceeds an existing safety cap, clear it and show an explicit unavailable state; state any snapshot-level bounds in the adjacent explanation.

Inspection performs no recording, transcription, model/effect/proxy request or DOM action. It stores no payload in local/session storage or logs. Clear payload and locally supplied command/effect data on hide, STOP, target navigation/removal/invalidation and options close. Rapid show/hide, changed preview kind and late responses must not repopulate a hidden/stale region; fence replies by current request/target. Changing kind clears the previous payload before another explicit show.
